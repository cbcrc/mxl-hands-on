Two layers: the engine and the ABI

Everything green is scenario vocabulary invented by this tool. Everything blue is an argument that actually crosses into libmxl. Confusing the two is the single most common way to misread a run.
engine only — never reaches libmxl crosses the ABI boundary lane bookkeeping

1 · One step, end to end

A step is a line of JSON. By the time libmxl sees anything, every expression has been flattened to a number or a pointer — the ABI has no idea a lane, a cursor or a mode ever existed.

The one consequence worth memorising. An index is chosen by the engine, and OTS is derived from the index by libmxl — it is never stored in a grain. So the engine's arithmetic is the media time. That is why a scenario can run slower than real time and still produce timestamps a real consumer accepts.

2 · Lanes, cursors, and what is shared

A lane is a thread with a step list, a cursor and a program counter. Lanes never share those. They do share the handle registry and the event log — which is why one lane can create a writer another lane could name, and why the console shows a single interleaved timeline.

3 · delay_before_ms vs pace

Both make a step wait, and they are not interchangeable. One measures from the previous step; the other measures from the grain's own OTS. Only the second keeps a writer on the media grid, and only the first is affected by the transport bar's delay scale.

Three asymmetries that bite. The transport bar's delay_scale multiplies delay_before_ms only — a paced step ignores it entirely. pace and delay_before_ms are mutually exclusive on one step. And pace needs a resolved unsigned index plus a handle whose grain rate is known, because it aims at that index's OTS. A step may carry both offset_ms and jitter_ms: the first biases every grain the same way, the second scatters them.

4 · The four index modes

One expression shape, four sources for the number. offset is plain signed arithmetic applied last, to whichever number the mode produced — it is not a length, a count or a duration.

pace.jitter_msengineA random shift, redrawn per step from a uniform distribution over ±jitter_ms. Where offset_ms is a bias, this is spread — it exists to stop many lanes hitting the ring in lockstep. The RNG is one per lane thread, seeded from the lane name, so lanes do not jitter together and a run is reproducible per lane. Must be ≥ 0.

Reading the log

Every step appends one JSON object to /log. Some of its fields are the engine's account of what it did, some are the ABI's answer, and a few of the most useful numbers are neither — they are derived. Fields appear only when they apply, so a short event is normal.

On every event

fieldmeaning
seqMonotonic across all lanes. /log?since=<seq> resumes from it; a 410 means the tail was evicted and carries the cursor to re-sync from.
lane / step_idWhich lane ran it and the step's id from the scenario.
t_wall_nsTAI nanoseconds, stamped after the call returns — so a blocking step's row appears in the log at its end, not its start. A string, because the value exceeds JavaScript's safe integer range.
duration_usBrackets the adapter, not just the ABI call: argument marshalling, the payload fill, and the call itself. Subtract fill.fill_us for the call alone. Excludes any delay_before_ms or pace sleep.
ok / statusstatus is the mxlStatus by name. ok:false accompanies any non-OK status — including the ones a scenario is trying to produce, so a red row is often the point of the step rather than a failure of it.
errorPresent when the step failed before the ABI — an unknown handle name, a bad argument type, an index expression that would not resolve. No status, because nothing was called.

What the engine did

fieldmeaning
resolvedEvery index expression flattened to the number that actually crossed. {"index": …, "head": …, "flow": "discrete"}. This is the field that tells you what the step really asked for — and it is named resolved, not args_resolved.
delay_msThe relative sleep that ran before the step, after delay_scale was applied. Absent when zero.
pacedeadline_ns is the unjittered target — consecutive values are exactly one grain apart, which is what makes an offline drift check possible. late_ms is the wake measured against the jittered target. jitter_ms appears only when one was drawn, capped:true when the sleep hit the 5 s cap.
cursorOnly on setCursor: the index the lane was seeded to. Those events also carry abi:false, which is how you tell a pseudo-call from a real one.
stored_asThe registry name a creating call produced.
(released)Not a log field, despite looking like one: released comes back on the /reset response, naming the handles destroyed in release order. It cannot be in the log, because reset clears the log — which is also why the next /log?since= answers 410 with a fresh cursor rather than an error.

The timing numbers, and which ones lie

fieldmeaning
ots_nsThe grain's origin timestamp, derived from its index by the SDK. A string. Never Number() it and never subtract two of them in JavaScript — the low three digits are exactly the resolution you are trying to see.
age_msread wall clock − OTS. How old the grain was when read. Signed: negative means you read a grain whose media time is still in the future.
stampOnly when the step set verify_stamp and the writer set fill.stamp. write_ns is the writer's clock at fill time; transit_ms is read wall − write wall, the true end-to-end delay; matches says the stamped index equals the grain's, which is how you catch a stale or torn read.
waited_msHow long a blocking call actually blocked. Meaningless on its own — read it against timeout_ns. Roughly equal means the deadline expired; much less means it woke on a commit. A timeout never arrives as MXL_ERR_TIMEOUT; it arrives as MXL_ERR_OUT_OF_RANGE_TOO_EARLY, indistinguishable from an unreachable index except by this number.
fillfill_us is the payload write, bytes how much, stamp_ns the value planted. On a 1080p v210 grain the fill is ~80% of the step.
write latenessDerived, not a field: age_ms − stamp.transit_ms = write wall − OTS. How late the producer was. Both terms come from the same grain, so it carries none of the frame quantisation that age_ms and waited_ms do — it is the only exact measure of source delay in the log, and it is the column M15's timing panel renders.
Four ways to misread a run. A blocking step's row lands at the moment it finished, so the log's order is completion order, not start order. duration_us is the adapter, not the ABI. age_ms and waited_ms both carry ±half a grain of quantisation, because a wait ends when the grain nearest the target commits — use write lateness when the number has to be exact. And the first event of each distinct call in a process is an outlier (~10 ms for mxlCreateInstance, and a first OpenGrain pays the page faults for the whole ring): run a call once before trusting its duration_us.
